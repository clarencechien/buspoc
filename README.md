# buspoc — 中和→永和 下班公車決策 POC

## 3D 公車地圖（此 branch 新增）

新增 GitHub Pages 靜態網頁 `web/`：Mapbox 3D 建築、公車定位標籤與直線距離、可修改路線及 A/B 點、定位與方向篩選。預設 57 / 706 / 243 / 214直 / 橘3。

- [分階段計畫](docs/MAPBOX_3D_PLAN.md)：先 Web，再 PWA / WebAR。
- [部署與使用說明](docs/MAPBOX_SETUP.md)：Mapbox token、TDX Worker、GitHub Pages。
- `node --test` 執行測試；`python3 -m http.server 8000 --directory web` 本機開啟。

即時資料需部署 TDX 代理並設定憑證；示範模式有明確標示。距離不是 ETA，目前不做 A→B 路線推薦。下方保留原始研究結論，這次地圖是新增的視覺化方向。

用真實 TDX 資料回答一個限縮到極致的問題:
**下班走出銀行,該走連城路軸(57/706/243/214直)還是錦和路軸(橘3)?該停哪一站?**

結論:**問題已解,不需要做成 app。** 完整分析見 [`report.md`](report.md)。

## 最終決策規則(背下來就能用)

```
走出銀行(平日 17:00–19:00):
  下一班橘3 ≈ 中和站表定 + 5.6 分通過建一路(表定:17:00/17:20/17:50/18:20/19:00/19:40/20:20)
  若它落在「現在 + 步行2分 + 容忍等待」內
    → 走建一路(146m)搭橘3,仁愛路(一)下車(離門口 100m),車程約 20 分
    → 站上等超過表定 +12 分沒車(漏班率 3%)就撤退連城路軸
  否則
    → 走連城中正路口(256m),搭先到的 706 或 57,捷運頂溪站下車(259m)
  台貿一村不值得多走 289m;跳蛙不值得專程等;243/214直 不需納入
```

## 主要發現(10 個平日、17:00–19:30 實測)

| 發現 | 數字 |
|---|---|
| 公告班距失真 | 706 公告 7–10 分,實際間隔 p90=28 分、串車率 17–19%、最長斷檔 45 分;57 公告 8–12 分,實際 p50=12、p90=20 分 |
| 合流效應才是重點 | 57+706 在連城中正路口合流後,隨機到站期望等待僅 4.9 分 |
| 橘3 是最快路徑 | 建一路→仁愛路(一)車程 p50=20 分,門到門約 23 分+等待;連城路軸最快 34 分。**抓對橘3 比預設答案快 10 分鐘以上** |
| 橘3 準點特性 | 到建一路 = 表定 +3~+10 分(p10–p90),不早發、慢有上限,漏班 2/70 |
| 跳蛙可搭但無優勢 | TDX 班表缺往頂溪方向;歷史資料還原事實班表:每天傍晚 3 班(約 17:33/18:05/18:55 過連城中正路口),車程 27 分與 57 相當 |
| 意外發現 | 建一路站(146m)比錦和路站(373m)離銀行更近且站序在後——錦和路軸沒有上下游權衡 |

方法上的兩個坑(照 handoff 預防成功):
- 新北資料裡**同一根站牌在每條路線各有一個 StopUID**,必須用該路線自己的 UID 查即時/歷史資料(對照表:[`stops.json`](stops.json))。
- 「實際到站」定義寫死為 A2 進站事件(`A2EventType==1` 的 GPSTime,按車牌+趟次去重),全程一致。

## 檔案

| 檔案 | 用途 |
|---|---|
| `report.md` | 主要產出:完整分析與 go/no-go 判斷 |
| `fetch_static.py` | 站牌/路線/班表抓取、下車點驗證(Phase 1) |

注意:TDX 按來源 IP 限流,腳本已內建節流與 429 退避;歷史端點忽略 OData 參數、回傳整天全市 NDJSON(約 900MB/天),`fetch_history.py` 用串流過濾處理。

## 未來可能的方向(按價值排序)

1. **ETA 校正曲線(唯一還缺的資料)** — TDX 顯示「N 分後到」的實際準度沒人量過。用任一常駐環境(cron)在平日 16:30–20:00 每分鐘抄一次 N1 快照,一個月即可畫出「顯示 N 分 → 實際 N′ 分」對照。這是所有公車 app 都沒有的東西。
2. **甩站率估計** — 精度天花板。唯一觀測手段是人工回報「這班沒上到」,一個月樣本即可把等待期望值乘上 1/(1−x) 修正。
3. **上班方向(永和→中和)** — 同一套腳本換方向重跑即可,邊際成本一天。
4. **多模式比較** — 同一 OD 加入「橘3 vs 走到捷運頂溪站轉乘 vs YouBike 直騎」:YouBike 即時可借 + 北捷 LiveBoard 都已驗證可用,材料齊全。
5. **通用化** — 把「兩軸 N 站 M 路線」的決策器參數化成任意 OD 的設定檔:本專案的管線(釘 StopUID → 拉歷史 A2 → 算合流等待/車程/準點)對任何雙北通勤走廊都成立。
6. **台鐵/捷運誤點分析** — 台鐵 TrainLiveBoard 有即時誤點但無官方歷史;自建收集器逐日累積,可做「哪班區間車最不準」這類分析。
7. Cloudflare Worker 一頁 dashboard — 已完成規劃與 UI mockup,判定暫不需要;若哪天想做,計劃與 mockup 都在(見 session 紀錄)。

## 為什麼不做 app

零資料規則(班表 + 步行時間)已覆蓋 100% 情境,其中 73% 的答案(走連城路軸)幾乎不會錯;
剩下 27%(橘3 窗口)背下班表加減 5 分鐘就能處理,漏班止損一條規則搞定。
即時資料能再買回的,只有橘3 那 7 分鐘的不確定區間——值一個網頁書籤,不值一個系統。
